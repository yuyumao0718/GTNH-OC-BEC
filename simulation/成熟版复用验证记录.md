# 成熟版复用验证记录

2026-11-05，范围为 `simplified-shared-input` 的成熟版流程复用。修改前基准为 `7858ffd`，单台成熟版来自用户上传的 `cache_install.lua`。运行约定见[实施边界](../配置界面与加工逻辑实施方案.md)，原始测量见 [mature-flow-comparison.json](mature-flow-comparison.json)。

**实际改动**

- 同台先设置所有参与节点的最大并行，再连续开启。正常取料不再按四节点配额设置并立即开启。
- 先推进已有加工和装卸，再准备一台新阵列。有阵列正在加工时，参数准备约 0.15 秒后让出；全部参数完成后，开启动作保持连续。单次组件调用无法中途取消。
- 已确认空闲且仍然关闭的节点复用确认结果；开启后继续查询取料状态，重启后重新核实。不增加每个参数的保存。
- 恢复检查单独分段；已取料节点不重新开启。资源预留、蜂群排队、fastTier、算力奇点、保存退出和 GUI 布局保持现有规则。

运行源码只修改 `ma_core.lua`。蜂群选择、样板算法、装卸、预缓存、保存、恢复兼容和界面模块没有复制成另一套实现；等价部分直接保留。独立安装器由同一源码重新生成。

**复核结论**

按调用链核对 `schedule → recoveryIntakes → arrayTick → array → admissionTick`，以及 `worker`、`recover`、`pause`、装卸归属和 GUI 读取。新增准备信息均在运行内存，不进入续做文件。算力奇点已经登记的节点跳过设置和开启；共享子网仍在整次分配余量核对后才放行下一单。

复核中发现并处理了三处问题：整台参数设置会延迟其他阵列的阶段检查，按用户确认加入准备阶段的短暂让出；让出后反复查询尚未开启的空节点，改为复用已经确认的状态；本轮刚从等待进入加工的阵列也纳入优先照顾范围，避免新取料准备占满整轮。没有新增配置、自动修复或调度策略。

单台成熟版的阶段定位、参考节点选择、最低可用等级和 fastTier 结果与当前程序一致。原始屏蔽层完整模拟实际装载顺序为 T4→T1→T3→T1，全部节点处于 1530 时下一次完整决策请求并装载 T1。用户截图中持续提供 T4 的现场没有复现，不能将本次修改描述成已确认修复该现场原因。

**性能对照**

模型使用 20 TPS、同步组件调用 1 tick、ME-IO 处理 1 tick；每级一套共享蜂群，每套 30720 个。直接调用、GPU 绘制和磁盘的实际墙钟时间未计入。下表时间从模拟原料首次到达计算，不是实机耗时。

普通场景为原始屏蔽层，每台 16 节点、每节点 3840 并行，工作量随阵列数增加。快速场景每台分配 16 份，满足 fastTier 条件。只比较同一行修改前后，不能用不同行计算扩容收益。

| 阵列数 | 普通场景修改前 → 后 | 快速场景修改前 → 后 | 同台首末节点取料间隔修改前 → 后 |
|---|---|---|---|
| 1 | 40.50 → 40.35 秒 | 2.30 → 2.05 秒 | 1.15 → 0 秒 |
| 2 | 57.55 → 57.15 秒 | 4.55 → 4.15 秒 | 2.00 → 0 秒 |
| 6 | 155.90 → 154.70 秒 | 12.60 → 11.40 秒 | 5.65 → 0 秒 |
| 10 | 254.15 → 252.15 秒 | 20.60 → 18.60 秒 | 9.80 → 0 秒 |
| 30 | 745.80 → 739.75 秒 | 60.70 → 54.65 秒 | 32.40 → 0 秒 |

“0 秒”表示模拟中的同一个 tick，不是保证实机同时取料。单台成熟版在普通场景为 40.70 秒，快速场景为 1.60 秒；简化版保留共享资源和恢复记录的开销。普通场景的总调用次数仍高于成熟版，模型中的简化版与成熟版循环等待分别为 50 ms 与 100 ms，本次没有调整正常加工轮询周期。

交叠场景先由一台开始加工，再允许其余阵列接收第二单；两单各 61440 份。此处工作量固定，用于检查已有加工和新取料之间的影响。

| 阵列数 | 新取料期间最长加工检查间隔，前 → 后 | 总耗时，前 → 后 | 组件调用总数，前 → 后 |
|---|---|---|---|
| 6 | 0.50 → 0.40 秒 | 60.15 → 60.15 秒 | 160169 → 159430 |
| 10 | 0.65 → 0.65 秒 | 63.20 → 63.25 秒 | 163482 → 158915 |
| 30 | 0.75 → 0.65 秒 | 119.40 → 120.95 秒 | 106944 → 82530 |

取料集中和及时让出不保证所有负载总耗时下降：三十台交叠场景约慢 1.3%，但取料期间的加工检查更及时、总调用减少。共享蜂群争用仍是主要等待来源，没有增加蜂群配置感知派单。

上表的最长间隔只统计新订单正在取料的时段。整个交叠测试中的最大间隔分别为 1.35、2.50、6.50 秒，包括集中开工和共享装卸；不能把 0.65 秒解释成三十台全部运行状态的响应上限。完整字段及各阵列累计等待时间保留在 JSON 中。

**验证覆盖**

- `tests/run.py` 在 Lua 5.2 和 5.3 下运行完整回归，包括成熟版纯算法差分、整台设置后开启、重复参数复用、算力奇点、资源授权、共享池、Q/S/Ctrl+C、保存失败和长字符串分段写盘。
- 新增每个参数写入及开启动作后的 64 个中断点，另测已有加工期间部分参数已设置时的崩溃和 Ctrl+C。两种 Lua 均验证不重复取料、不丢产出。
- `simulation/save_scale.py` 对六、十、三十台分别运行普通模式和 fastTier，两种 Lua 共通过 1752 次保存及物理搬运中断重放；按运行结果核对产出、蜂群归属、正常节点关闭次数和过滤写入次数。
- `tests/gui_preview.py` 渲染 80×25、120×38、160×50。复看运行页、取料状态和 16 节点两行长进度条；没有为 GUI 新增设备读取。
- `tests/package.py`、`tests/test_install.py` 校验独立安装器、压缩包与源码一致，新装和覆盖安装保留配置及续做文件。

测试未连接游戏存档，不能证明服务器长期运行、低 TPS 或世界库存与 OC 存档分别回滚时的行为。正式游戏更新仍先完成退出或暂停保存，再运行新安装器和 `bec_multi.lua run`。
